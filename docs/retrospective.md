# Ретроспектива: AI-first развитие UI-проекта

## Итог

Пройдены фазы 0–8, от одного Gradle-теста до GitHub Actions с Allure на Pages, уведомлений в Telegram и Jenkins. Каждая фаза шла по схеме «согласование → реализация → проверка → отдельный коммит». План со статусами, решениями и результатами проверок лежит в [docs/plans/ui-test-project.md](plans/ui-test-project.md).

Не проверены: отправка в Telegram из Jenkins (не стал заводить Credentials на общем Jenkins) и часть Telegram-исходов в CI, их покрывают unit-тесты.

## Где AI ошибся и как это поймали

| # | Ошибка | Как заметили | Какая проверка поймала бы раньше |
|---|---|---|---|
| 1 | Проверка в новом тесте была слишком слабой: `text("selenide")` и `urlContaining` пропускали переход в `selenide/selenide-appium` | Мутация: подменили ссылку на чужой репозиторий, тест остался зелёным | Мутационная проверка каждого нового assertion сразу при написании: «упадёт ли тест, если поведение сломать?» |
| 2 | Первая гипотеза о нестабильности поиска («Enter нажимается раньше гидрации React») оказалась неверной | Замер: в 12 открытиях `/search` приложение уже было загружено к возврату `open()` | Измерять до того, как объяснять. Добавленное ожидание `loaded` не лечит сбой, а только делает причину падения понятной |
| 3 | В CI Chrome не запускался (`No usable sandbox`), хотя локально всё работало | Первый же реальный запуск в GitHub Actions; причину установил отдельный диагностический прогон: AppArmor на ubuntu-24.04 | Проверка браузера на целевом runner ещё до написания полного workflow. Не заменять это решение на `--no-sandbox` без диагностики |
| 4 | Временный коммит создался, хотя `actionlint` нашёл ошибку в YAML: команды были связаны через `;`, а не `&&` | Прочитали вывод и увидели, что коммит есть, а линтер упал | Pre-commit hook с `actionlint` или строгая цепочка `&&` |
| 5 | Настройка concurrency в Actions (одна общая группа) отменила один из трёх одновременных запусков: `cancelled` вместо `failure` | Сверка фактического статуса с ожидаемым | Читать документацию concurrency про «один ожидающий запуск в группе» до выбора настройки, а контролируемые падения пушить по одному |
| 6 | Частый опрос GitHub API исчерпал лимит в 60 запросов в час | Ошибки `KeyError` / `rate limit exceeded` вместо статусов | Опрашивать реже и учитывать лимит, либо пройти `gh auth login` с личным токеном |
| 7 | Повторяющиеся ошибки экранирования в `sed`, regex и Python при правках файлов (`\n`, `\\`, скобки) | `assert` в скриптах правки, `git diff --stat`, `actionlint` | Править через структурные инструменты или Edit, а не однострочники; проверять diff после каждой правки |
| 8 | В разведке Jenkins код выхода `tail` приняли за код выхода Chrome | Сверили с текстом ошибки и наличием DOM в выводе | В диагностических скриптах не ставить `\| tail` перед `echo $?` |

## Что сработало

- **Проверять, а не верить на слово.**
  - Workflow, который «написан», ещё не значит «работает»: каждый сценарий подтверждался реальным запуском (успех, падение assertion, ошибка компиляции, нет результатов, неверный токен).
  - Факт push каждый раз сверялся по `git ls-remote`. Так несколько раз выяснялось, что push фактически ещё не дошёл до форка.
- **Версии брать из реестров и `--help`, а не из памяти модели.** Так нашлась ловушка `allure-junit5` против `allure-jupiter`. Валидатор Jenkins перед первым запуском показал, что Jenkinsfile синтаксически корректен.
- **Компромиссы по безопасности согласовывать явно и записывать в план вместе с ограничениями:**
  - `sysctl` в GitHub Actions вместо `--no-sandbox`;
  - `--no-sandbox` только в Jenkins, потому что сборка в контейнере агента идёт от root;
  - отказ от общих Credentials на shared Jenkins.

## Что сделаю иначе в следующий раз

- Сразу дать агенту доступ к чтению CI (`gh auth login`), чтобы он сам читал логи и артефакты, а не просил их скачивать.
- Проверять окружение CI (браузер, пользователь, песочница) диагностикой до основной реализации.
- Мутационно проверять каждый новый assertion сразу при написании.
